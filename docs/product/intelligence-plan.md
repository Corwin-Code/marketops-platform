# 智能化运营方案与接入排期（Ozon 试点店铺）

> 状态：Owner 已批准（2026-09-29，#58）；P1 已完成（#59），P2 进行中。
> 试点店铺和试点商品是真实店铺。读取直接对真实账户进行；任何写入都要逐项取得 Owner 同意、换用有写权限的 API key，并走完整安全链后才启用。

## 1. 目标

平台要回答两个问题：

1. **为什么卖不动**：用平台数据得出有证据的诊断结论。
2. **怎么卖好**：给出具体、可执行、算过账的改进动作，执行后跟踪效果。

衡量标准是试点店铺的出单、搜索需求转化和单件利润，不是页面或功能的数量。

### 2.2 试点店铺的诊断事实（汇总）

- **商品结构**：41 个商品，按标题是同一类目下的 4 个款式（分别有 20、9、6、6 个尺码或颜色变体；Ozon 自己的“型号”分组是 39+1+1，不能当作款式）；全部在售。
- **库存**：11 个无库存，在搜索中不可见；它们所在款式的其他在售变体都有搜索需求。
- **价格竞争力**：13 个价格指数 RED、1 个 YELLOW，含促销价比 Ozon 站内竞品最低价贵约 1.3–2.2 倍。
- **搜索与成交**：30 个有库存的商品近 7 天有明显搜索需求，但全店 0 下单。
- **成本与费用**：41 个商品都填了成本价（`net_price`）。价格接口返回的 FBS 销售佣金为 52%，另有物流费和收单费。
- **单件利润**：
  - 按当前售价，全部商品单件为正利润，约占售价的 21%–40%（物流按最高档，未扣增值税）。
  - 有竞品价的 14 个商品，按竞品最低价卖会全部亏损：保本价是竞品最低价的 1.29–1.73 倍。
- **内容**：描述只有 116–367 个字符；每个商品有 14–22 张图。

**结论**：单纯降价解决不了问题。平台要同时看价格、成本结构、搜索需求、内容和促销，才能给出可行的建议，这是本方案的核心。

### 2.3 其余业务区的真实情况

Slice 001–004 的引擎都在 main，但**没有合成数据**：
- 输入要么来自 Ozon（目前只有价格、平台库存、可售状态），要么靠人工录入或表格导入，其余的没有任何来源。
- **映射是总闸门**：试点商品没有内部 SKU，也没有映射（`core.listing_mapping`），而：
  - Slice 001 诊断先检查映射，未映射就是 `DATA_BLOCKED`；
  - Slice 002 只为已确认映射的商品生成风险卡；
  - Slice 004 的 Listing 辅助要求成员已映射。

| 业务区 | 缺口 |
| --- | --- |
| 001 诊断与改价 | `MetricEngine` 不读下单件数；`core.economics_projection_profile` 没有写入方，所以保本价、最低价一直不可用；`RecommendationService.propose` 没有调用方，改价建议不会生成；没有登记 Ozon 改价端点 |
| 002 缺货风险 | 销量取自 `ledger.sales_fact`，没有来源；在途库存靠人工证明；Ozon 的下单件数和在途数量都没被读取 |
| 003 广告 | 广告相关表没有任何写入方；没有 Performance API 适配器 |
| 004 Listing 与促销 | 描述、展示、促销、官方汇总观测（`core.lc_*`）全部来自人工录入；内容评分和流量没被读取 |
| AI | `ProjectionBuilder` 只读 `mart.metric_value` 和 `mart.diagnosis_finding`；只有 SKU 诊断解释和 Listing 辅助两个用途 |

## 3. 智能化架构：四层

```
L1 确定性诊断 ──▶ L2 Qwen 解读 ──▶ L3 受控动作 ──▶ L4 效果跟踪
（指标、规则、算账）  （解释、排序、方案）  （审阅、审批、执行、回读）  （前后对比、周复盘）
```

- **L1 确定性诊断**：
  - 扩展现有 `analyticsdecision` 引擎（`MetricEngine`、`DiagnosisEngine`、`PriceEconomicsCalculator`），不另起一套；
  - 新指标写入 `mart.metric_value`，新规则的结论写入 `mart.diagnosis_finding`，规则版本升到 2；
  - 这样 AI 投影、优先级队列、定价审阅都能直接使用；
  - 这是官方口径：页面上的"结论"首先来自这一层，没有 AI 也能用。
- **L2 Qwen 解读**：
  - 只读取 L1 的指标、结论和经批准的字段，用于解释原因、给相互竞争的假设排序、说明不确定性、写出行动方案和俄语内容草稿；
  - 不计算价格和利润，不能执行；
  - 模型不可用时页面退回 L1。
- **L3 受控动作**：
  - 每条建议对应一个动作能力（改价、内容修改、补货 Case、促销、广告），进入现有的审阅与审批流程；
  - 平台写入走完整安全链：
    - 证据化建议 → 确定性 Guardrail → 影响预览 → 人工审批或 Owner 预授权；
    - 幂等 Command → Readback → Audit → Kill Switch。
- **L4 效果跟踪**：
  - 每周快照；
  - 已执行的动作按固定窗口做前后对比；
  - Qwen 写周复盘，指出有效的动作和需要调整的地方。

## 4. L1：诊断模型

### 4.1 单件经济

- **计算引擎**：复用 `PriceEconomicsCalculator`，组件包括：
  - 佣金：按售价的百分比；
  - FBS 物流（首公里、干线、末公里）和收单费：固定金额；
  - 增值税估算。
- **输入**：
  - 费率来自 `/v5/product/info/prices`，即平台公布的当前费率，默认按最高档；
  - 成本来自 `net_price`（Owner 已同意作为 COGS 来源），记为 Cost Version。
- **需要扩展 profile**：现有 profile 按店铺加履约方式划分，但 Ozon 的物流费每个商品不同。需要扩展到商品级组件，并由 Ozon 费率观测自动写入。
- **扩展后可得**：`BREAK_EVEN_PRICE`（保本价）、`MINIMUM_PRICE`（满足利润下限的最低价）、任意价格下的单件利润。
- **计算规则**：金额一律用 decimal 加币种，只在同币种之间计算。
- **Estimated 标记**：出现第一笔真实结算（finance accrual）之前，利润类结论一律标为 Estimated，并注明所用档位。
- **缺数据**：缺成本或费率时，结论是"单件经济未知"，不会按 0 计算。

### 4.2 诊断规则（`DiagnosisEngine` 第 2 版）

**沿用的规则**：
- `STOCKOUT_RISK`（无库存）、`NEGATIVE_MARGIN`、`PRICE_BELOW_MINIMUM`、`ADVERTISING_INEFFICIENT`；
- `LOW_IMPRESSION`、`LOW_CLICK_THROUGH`、`LOW_CONVERSION` 需要曝光、点击和转化数据。没有 Premium 时这些数据拿不到，规则会如实标为"所需指标不可用"。

**新增的规则**：

| 编码 | 含义与判断 | 建议动作 |
| --- | --- | --- |
| `LISTING_NOT_SELLABLE` | 平台状态不可售或被隐藏 | 处理状态、审核问题 |
| `DEMAND_NOT_CONVERTING` | 在售、有库存，近 7 天搜索人数 ≥ 阈值，下单 0 | 根据下面各条判断原因 |
| `PRICE_GAP_REDUCIBLE` | 价格指数 RED/YELLOW，且最低价 ≤ 竞品最低价 | `PRICE_CHANGE`（给出价格区间） |
| `PRICE_GAP_PARTIAL` | 保本价 ≤ 竞品最低价 < 最低价 | 需 Owner 决定是否接受低于下限的利润 |
| `PRICE_GAP_STRUCTURAL` | 保本价 > 竞品最低价，降价无法在保本前提下追平竞品 | `COST_DATA_REVIEW`（成本、履约方式、采购），或靠内容与定位做差异化 |
| `LOW_SEARCH_EXPOSURE` | 在售、有库存，搜索人数低于阈值，说明商品只出现在很少的搜索里 | `LISTING_CONTENT_REVIEW`（标题、属性） |
| `CONTENT_BELOW_TARGET` | 内容评分低于阈值，或评分组里有未满足的条件 | `LISTING_CONTENT_REVIEW` |
| `PROMOTION_OPPORTUNITY` | 可以参加 Ozon 活动，按活动价算出的单件利润 ≥ 下限 | 人工参加活动并留痕 |
| `AD_BLOCKED_BY_FUNDAMENTALS` | 存在不可售、无库存或结构性价格差时，不建议给该商品投广告 | `ADVERTISING_REVIEW` |

**规则约定**：
- **阈值**：沿用现有 `marketops.analytics.thresholds` 配置，由 Owner 定值；每条结论都记录规则版本和所用阈值。
- **排序**：先按严重程度，再按影响。影响以搜索人数表示需求规模，同时参考单件利润空间。
- **证据等级**：价格指数和搜索数据是 C 级（平台分析），只用于诊断和排序；不会自动改价（HR-07）。

## 5. L2：Qwen 智能层

### 5.1 用途

| 场景 | 输入（经批准的投影） | 输出 |
| --- | --- | --- |
| 店铺周诊断 | 店铺汇总、各规则的命中数与影响、优先级最高的商品 | 一句话结论、3 个最优先的动作、不确定项 |
| 商品诊断 | 该商品的指标、规则结论、单件经济、搜索词 | 原因解释、假设排序与把握程度、行动方案 |
| 内容与搜索词优化 | 标题、属性、描述、类目属性要求、内容评分组、搜索词 | 俄语标题、描述、属性补全草稿，以及它们覆盖了哪些搜索词 |
| 促销取舍 | 活动、候选商品、按活动价算好的单件利润 | 建议参加或放弃哪些活动，以及理由 |
| 广告复盘 | 广告活动的花费、曝光、点击、下单（接入后） | 效率解释、调整建议（出价以规则算出的数值为准） |
| 周复盘 | 已执行动作的前后对比 | 哪些动作有效、下一步怎么做 |

### 5.2 实现方式（沿用现有 AI 边界）

- **投影**：
  - 扩展 `ProjectionBuilder`：`SKU_GROWTH_PROFIT_DIAGNOSIS` 升到 v3，加入新指标和搜索词；
  - 新增 `STORE_DIAGNOSIS`（以店铺为对象）；
  - `LISTING_ASSISTANCE` 升到 v2，加入搜索词、类目要求和评分组；
  - 字段逐个登记在 `ops.ai_projection_field`，带分类和保留策略。
- **Prompt**：沿用代码内按版本管理的模板，要求中文输出，俄语草稿保留俄语。
- **输出与校验**：
  - 沿用 facts / inferences / recommendations / unknowns 结构和 `OutputValidator`；
  - fact 必须引用投影里的值或规则结论，数字只能照抄投影，不能自行计算；
  - 建议只能从 `actionCapability` 枚举中选；
  - 校验不过的输出不展示。
- **生成与缓存**：
  - 建议按需生成（点击"生成解读"），按事实摘要（digest）缓存，事实不变就不重复调用；
  - 每日采集完成后自动生成店铺周诊断，作为可选项。
- **审计与降级**：调用写入 `ops.ai_invocation` / `ai_output_claim` / `ai_claim_evidence`；provider 停用或超时，页面只显示 L1。
- **数据出境**：
  - 百炼服务在 `cn-beijing`，发出去的字段由 Owner 决定（见第 8 节）；
  - 建议：商品内容、价格、竞品价、搜索词可以发；成本和利润只发比例（例如"保本价比竞品最低价高 56%"），不发原始成本；
  - 不发买家数据和任何凭证。

### 5.3 页面形态（从数据到结论）

**店铺诊断页（首页）**：
1. **本周诊断**：
   - AI 摘要卡：一句话结论、3 个优先动作、不确定项，每句都能点开证据；
   - 下方是 L1 结论条，例如"11 个商品无库存，它们的同款在售变体都有搜索需求""14 个商品价格高于竞品，降到竞品价会亏损"。
2. **问题清单**：
   - 按问题而不是按商品组织；
   - 每个问题列出受影响的商品、证据、建议动作和"去处理"入口。
3. **商品表**：在现有列之外，新增搜索人数、诊断标签、单件利润率。

**商品详情抽屉**，依次显示：
- 诊断结论；
- AI 解读；
- 建议动作：入口到定价审阅、内容优化、补货 Case、促销留痕；
- 证据：现有信号、搜索词、单件经济。

**复盘**：已执行动作的前后对比和周复盘。

## 6. 各业务区接入方案

"已授权"指当前 API key 的角色已包含该端点（Product read-only、Report、Returns read-only、Actions read-only）。

### 6.1 主数据与映射（所有业务区的前提）

- **生成内部商品**：从 Ozon 目录生成内部商品和变体，`sku_code` 取 `offer_id`（经现有商品目录维护接口）。
- **建立映射**：
  - 用现有的 `ListingMappingService` 按条码或 `offer_id` 生成映射提议；
  - 映射必须有确认人（`confirmed_by_user_id`），由 Owner 批量确认。
- **成本**：以 `net_price` 生成 Cost Version，来源和观测时间写入数据。

完成后，Slice 001 的诊断、002 的风险卡、004 的辅助都可以对试点商品运行。

### 6.2 店铺诊断（首页）

- **读取**：第 2.1 节的全部数据；另外标准化 Ozon 的费率和评分组。
- **展示**：`mart.diagnosis_finding` 里的规则结论，以及 Qwen 解读。
- **AI**：店铺周诊断、商品诊断。
- **写入**：无，只把用户引导到各业务区的动作。

### 6.3 Slice 001 SKU 增长与利润 · `PRICE_CHANGE`

- **指标**：`MetricEngine` 增加下单件数（取自流量数据）、搜索人数、比竞品贵多少、内容评分，以及由商品级 economics profile 算出的保本价和最低价。
- **建议**：
  - 由规则结论生成 `PRICE_CHANGE` 建议，补上 `RecommendationService.propose` 的调用方；
  - 价格区间只来自 L1 和 Guardrail（最低利润、最大调价幅度、冷却期）；
  - 建议进入现有的定价审阅。
- **写入**：
  - 端点：`/v1/product/import/prices` 改价，回读 `/v5/product/info/prices`；
  - 前提：当前 key 没有这项权限，需要带价格写权限的 key 和 Owner 对这项能力的明确同意；
  - 启用方式：先对 1 个商品灰度，验证回读和 Kill Switch 后再扩大范围。
- **AI**：沿用 SKU 诊断解释，投影升到 v3。

### 6.4 Slice 002 缺货与可售风险

- **需求**：改用 Ozon 下单件数（在有销售事实之前），并参考同款在售尺码的搜索人数。
- **在途库存**：读取 `listing_stock_observation.inbound_quantity`。
- **按仓库库存**：FBS 分仓库存用 `/v2/product/info/stocks-by-warehouse/fbs`（已授权；v1 已停用）。
- **FBO 端点不适用**：`/v1/analytics/stocks`、`/v1/analytics/turnover/stocks` 都是 FBO 口径，而试点店铺只做 FBS。
- **写入**：无（Slice 定义如此）。
- **AI**：Slice 002 本身不用 AI；缺货原因只在店铺诊断里解释。

### 6.5 Slice 003 广告 · `AD_BID_CHANGE`

- **前提**：Performance API 是独立系统，凭证和鉴权方式不同（先换取访问令牌），需要：
  - 新的适配器；
  - 新登记平台档案和端点，并做真实账户核验；
  - 标准化到现有广告表（`core.ad_native_object`、`ledger.ad_object_fact` 等）。

  这一项工作量较大。
- **读取**：广告活动、按天统计（花费、曝光、点击、下单）、商品级统计和出价。
- **AI**：广告复盘；同时遵守 `AD_BLOCKED_BY_FUNDAMENTALS`，基本面有问题的商品不建议投放。
- **写入**：出价修改在读取稳定后再逐项申请同意。
- **顺序**：试点店铺目前价格和库存问题突出，广告排在价格、内容、促销之后。

### 6.6 Slice 004 促销与 Listing 转化 · `LISTING_DESCRIPTION_CHANGE`

- **内容**：
  - 描述（属性 4191「Аннотация」）、富内容（属性 11254）、属性和图片，已经由商品目录能力采集到 Raw；只需标准化写入现有的 `core.lc_description_observation` / `lc_display_observation`，替代人工录入；
  - 内容评分组也已在 Raw 里；
  - 类目属性要求 `/v1/description-category/attribute`：试点商品都在同一类目，只需一次调用；该端点未列入当前角色，需要探测。
- **促销（均已授权）**：
  - `/v1/actions` 活动列表；
  - `/v2/actions/candidates`、`/v2/actions/products`：可参加和已参加的商品，含最高活动价、推荐活动价和对应的曝光加成；
  - v1 版这两个接口 2026-10-13 停用，直接用 v2；
  - 写入现有的 `core.lc_promotion_observation`，由现有促销模拟按活动价计算单件利润。
- **AI**：
  - 俄语标题、描述、属性草稿，写明覆盖了哪些搜索词；
  - 促销取舍；
  - 草稿只供人审核。
- **写入**：

## 9. 边界与风险

- **平台分析不单独驱动调价**：价格指数、搜索数据属于 C 级平台分析，只用于诊断和排序。
- **AI 只给建议**：AI 不计算价格和利润，不能审批和执行；它引用的数字必须能追溯到事实或 L1 结论。
- **搜索数据有限**：只能查最近一个月，不含当天；没有 Premium 时拿不到排名位置，部分结论只能给出假设和把握程度。
- **限流与配额**：分析接口限流严格（下单数据每分钟 1 次、每天 50 次），定时采集必须排队并留有余量。
- **真实店铺写入**：默认关闭，按能力、店铺、商品范围逐项启用；每项都有 Kill Switch 和回读；超时不盲目重试。
